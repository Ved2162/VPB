## Additional verified root cause

A real signed request generated by the application was accepted at `https://test.payu.in/_payment` and returned HTTP 302 to `https://apitest.payu.in/public/`, which served HTTP 200. The existing CSP allowed the initial host but omitted this sandbox redirect host. `next.config.ts` now permits that exact HTTPS origin alongside the existing production hosts. The browser's initial action allowlist remains limited to the exact test and production `_payment` URLs.

The real hosted page rendered the payable amount and UPI, Cards, Net Banking, Wallet, EMI, Pay Later and NEFT/RTGS options. A new browser regression covers the observed test-host redirect under the application's actual CSP response headers.

## Actual PayU sandbox observations

- A signed Verify Payment lookup authenticated with the supplied test credentials and returned Not Found for an intentionally nonexistent reference. No charge was created by that lookup.
- Invalid cart quantity was rejected with HTTP 400. Valid initiation used the server-priced amount; repeated creation returned the same merchant attempt ID.
- A signed hosted request reached the real payment page. Authoritative status checking returned pending/initiated, and retry returned status recovery without another form or charge.
- A deliberately incorrect hash was rejected by PayU with its hash-calculation error page. Do not publish that raw diagnostic page: PayU's error content includes sensitive hash-generation details. Diagnostic artifacts remain ignored locally.
- A real sandbox Mastercard payment using PayU's published dummy card and OTP returned through the application's callback, passed authoritative verification and displayed Order Confirmed with an invoice for Rs 100. No card was saved.
- Cancelling the sandbox bank authentication requires confirming the simulator's dialog. It returns to PayU's payment options rather than automatically redirecting to the merchant. A subsequent application status check obtained authoritative failed/failed, enabling recovery and retry on the original order.
- An invalid-OTP experiment remained on the bank simulator; it is not evidence of a completed terminal-decline callback. Bank failure, duplicate callback, amount mismatch, outages and concurrency remain covered by the mocked backend/browser suites. Not every payment method was transacted in the actual sandbox.

All actual sandbox orders above used a disposable PGlite database and artificial customer data. Production stock, customer notifications and order records were not used for these transactions. The public domain's runtime settings and headers were checked separately; no authenticated customer purchase on the public production database was completed by this validation.

## Repeatable tests

1. Put the merchant's TEST key and salt in the ignored `.env.payu-sandbox.local` file using names `PAYU_MERCHANT_KEY` and `PAYU_MERCHANT_SALT`. Do not commit this file.
2. Run `npm run build`.
3. Start `node scripts/e2e-server.mjs --payu-sandbox`. This always constructs a disposable local database, forces test endpoints and disables external customer notifications. Without the flag, gateway traffic remains disabled as before.
4. In another terminal, run `npx playwright test --config playwright.payu-sandbox.config.ts`. The opt-in suite exercises real sandbox capture/callback/confirmation/idempotent checks and bank-cancellation recovery/retry. It refuses a server reporting production mode and aborts requests to Live PayU hosts. Screenshots, video and traces are disabled for this suite.
5. For ordinary regressions, use a fresh isolated server and run `npx playwright test tests/e2e/payu.spec.ts --config .payu-checkout.playwright.config.ts`. These tests mock or abort provider traffic. A single fixture login is reused across clean browser contexts so the suite itself does not exhaust the application's login budget.

Restart the disposable server between repeated full suites because saved profile contact details, pending attempts and login budgets are intentionally persistent inside a run. Do not weaken production rate limits to make tests pass.
